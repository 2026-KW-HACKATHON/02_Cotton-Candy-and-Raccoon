# #86 Android 마감 알림

일반·편한 화면의 공지 상세에서 날짜와 시간을 지정해 시스템 알림을 예약한다.
`summarized` 상태이고 마감 날짜가 있는 경우 하루 전·당일 날짜를 선택할 수 있다.
원문을 확인한 뒤 예약 버튼을 눌러야 실제로 예약된다. 키워드 서버 푸시는 #87 범위다.

## 저장 및 변경

- 날짜·시간은 휴대폰 현지 시간으로 해석한다. 예약 후에는 해당 시점으로 고정된다.
- Expo Notifications의 Android 예약 저장소가 예약 정보의 원본이다. 별도 앱 캐시를 중복 저장하지 않는다.
- 공지별 고정 identifier를 사용한다. Android의 같은 PendingIntent를 갱신하여 중복 예약을 막는다.
- 앱을 다시 열거나 설정에서 돌아오면 OS에 저장된 예약을 조회한다.
- 예약 변경·취소 전에 시작한 조회와 뒤늦게 도착한 조회 오류는 현재 결과를 덮어쓰지 않는다.
- 예정 시각이 지나도 OS에 예약이 남아 있으면 지연 가능성을 표시하고 취소 버튼을 유지한다.
- 예약 시각은 원문의 마감일 변경을 자동 추적하지 않는다. 변경 시 사용자가 다시 예약해야 한다.
- 알림 터치는 숫자 공지 ID만 허용하며, 앱 시작·온보딩·라우터 준비 후 상세로 이동한다.

## APK 빌드

`expo-notifications` plugin과 `SCHEDULE_EXACT_ALARM` 권한을 추가했으므로 새 APK가 필요하다.
JS 업데이트만으로 기존 APK의 네이티브 설정은 변경되지 않는다.

EAS 계정과 프로젝트가 설정된 환경에서 `apps/mobile` 기준:

```sh
npx eas-cli build --platform android --profile preview
```

`eas.json`의 preview는 APK 내부 배포용이다. 프로젝트 연결·서명 자격 증명은 빌드 환경에서
설정하며 저장소에 비밀 값을 넣지 않는다. 실제 공지 조회에는 기존 공개 Supabase 환경 변수도 필요하다.
로컬 알림에는 Firebase 서버 키나 Expo 푸시 토큰이 필요하지 않다.

## 실기기 확인 순서

1. Android APK를 설치하고 온보딩 후 실제 공지를 연다.
2. 알림 시각을 현재보다 2~3분 뒤로 직접 입력하고 알림 권한을 허용한다.
3. 휴대폰 설정의 특별한 앱 접근 → 알람 및 리마인더에서 이 앱의 정확한 알림 허용 여부를 확인한다.
4. 앱을 백그라운드로 보내 시스템 알림을 받고, 누르면 동일 공지 상세가 열리는지 확인한다.
5. 앱을 일반적으로 종료한 뒤에도 알림 터치로 상세가 열리는지 확인한다.
6. 같은 공지의 예약 시간을 변경하고 이전 시각에 중복 알림이 없는지 확인한다.
7. 예약 취소, 앱 재실행 후 예약 조회, 권한 거부, 일반·편한 화면을 확인한다.
8. 사용 기기·Android 버전·빌드·공지 ID와 수신 결과를 기록한다.

정확한 알림 권한이 없으면 설치된 Expo Android 구현은 부정확한 시각의 알람으로 대체한다.
절전·제조사 설정에 따라 지연될 수 있다. 설정의 강제 종료는 일반적인 앱 종료와 다르며
알림을 막을 수 있다. 자동 테스트는 실기기 수신 검증을 대신하지 않는다.

참고: [Expo 알림 문서](https://docs.expo.dev/versions/latest/sdk/notifications/),
[Android 알람 문서](https://developer.android.com/develop/background-work/services/alarms).

## 구현 검증 기록 — 2026-10-09

- TypeScript 검사와 프로젝트의 `npm run lint` 통과.
- Node 테스트: 날짜·권한·채널·예약 교체·취소·재조회·알림 진입을 포함해 검증.
- `expo export --platform android` 성공: Android 배포용 JS/Hermes 번들 생성 확인.
- APK 빌드와 실기기 수신은 미검증. 현재 PC에는 Android SDK와 빌드용 JDK가 없다.
  EAS 빌드도 실행하지 않았다. 위 실기기 완료 조건을 확인하기 전에는 이슈를 완료 처리하지 않는다.

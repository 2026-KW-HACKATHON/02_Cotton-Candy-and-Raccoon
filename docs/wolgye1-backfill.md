# 월계1동 과거 공지 보충 (#109)

상위 작업: #107. 기존 웹 디자인, DB 스키마, 정기 수집 정책은 변경하지 않는다.

## 공지가 적은 이유와 적용 범위

- `collect --source wolgye1 --mode new`는 첫 실행에서 일반 공지 5건을 기준선으로 삼는다. 다음 실행은 신규 글을 찾다가 기존 글을 만나면 멈춘다. `refresh`도 최근 일반 글 5건과 고정 공지만 갱신한다. 따라서 정기 실행만으로 과거 데이터의 빈 구간이 채워지지 않는다.
- 기존 무제한 `collect --source wolgye1`은 전체 게시판을 순회한다. `--limit`은 고정 글과 다른 동 글까지 포함한 앞쪽 건수 제한이므로 월계1동 공개 공지의 목표 건수와 일치하지 않는다.
- 2026-10-10 공식 [월계1동 게시판](https://www.nowon.kr/dong/user/bbs/BD_selectBbsList.do?q_bbsCode=1042&q_deptCode=1047)을 읽었을 때 일반 공지 2,300건 / 230페이지 / 페이지당 10건이었다. 첫 페이지에는 일반 공지 10건(2026-04-20~2026-10-06), 다른 동 고정 공지 8건이 있었다. 게시판 값은 이후 바뀔 수 있다.
- 공개 뷰 `app_notice_list`는 `is_visible`과 `dong_group != other`를 적용한다. 요약이나 쉬운말이 없어도 원문 공지는 노출된다. 앱은 `source=dong` 필터와 날짜·ID 커서로 페이지를 나눠 가져오며 전체 공지 수를 5건으로 제한하지 않는다. 분류 필터를 추가하면 표시 대상은 줄어든다.
- 운영 DB의 실제 저장 건수와 수집 이력은 이번 작업에서 조회하지 않았다. 위 설명은 코드상 원인과 공식 게시판 관찰이다.
- 월계2·3동까지 확대하려면 공식 목록과 담당 부서 검증, `dong_group` 제약(현재 `wolgye1`, `other`만 허용), 변환 모델과 앱 지역 구분 계약을 함께 바꿔야 한다. 이번에는 검증된 월계1동 게시판의 과거 자료를 보충한다. 다른 동 고정 글을 월계1동으로 바꿔 넣지 않는다.

## 실행 절차

`services/pipeline`에서 기존 방식으로 대상 `DATABASE_URL`을 주입한다. 출력에 연결 문자열이나 비밀 키는 포함하지 않는다. DB 계정에는 기존 수집 권한과 `SET ROLE anon` 권한이 필요하다. 공개 건수 확인은 읽기 전용 트랜잭션에서 실제 `anon` 역할로 실행한다.

```bash
# 먼저 범위 확인: 목록 HTTP 요청과 DB 읽기만 수행한다.
uv run pipeline backfill-wolgye1 --start-page 1 --end-page 3 --since 2026-01-01 --dry-run

# 확인한 동일 범위 저장 (페이지와 날짜는 시연에 필요한 범위로 선택)
uv run pipeline backfill-wolgye1 --start-page 1 --end-page 3 --since 2026-01-01

# 더 오래된 페이지를 별도 보충하거나 실패한 페이지를 다시 실행
uv run pipeline backfill-wolgye1 --start-page 4 --end-page 6 --until 2025-12-31

# 건수 제한 시험: 범위 후보보다 적게 제한되면 partial이므로 종료 코드 1
uv run pipeline backfill-wolgye1 --end-page 2 --limit 5 --dry-run
```

위 페이지·날짜 값은 사용 예시이며 자동 목표 건수가 아니다. `--end-page`는 필수이고 실제 마지막 페이지보다 크면 오류다. 날짜는 등록일 기준이며 양 끝을 포함한다. 날짜와 건수 제한을 주더라도 지정한 페이지를 모두 읽어 고정 글 중복과 충돌을 확인한다. 페이지 번호는 새 글 등록에 따라 움직이므로 재실행 전에 범위를 다시 확인한다.

저장 뒤 필요한 AI 처리는 기존 별도 명령을 사용한다. 보충 명령 자체는 AI API를 호출하지 않는다.

```bash
uv run pipeline process-stored --source wolgye1 --feature summary --limit 100
uv run pipeline process-stored --source wolgye1 --feature easy_text --limit 100
```

AI 명령은 이번에 보충한 ID뿐 아니라 해당 출처의 처리 대상을 선택한다. 건수와 비용을 확인해 실행한다. DB 보충 없이 코드만 배포해서는 웹의 공지 수가 늘어나지 않는다.

## 결과 해석과 실패 복구

- `before`, `after`, `delta`: 월계1동 저장 건수와 공개 뷰 건수. 같은 DB에 다른 수집기가 동시 실행되면 그 변경도 차이에 포함된다.
- `saved_count`: 이번에 저장 성공한 건수이며 신규 삽입 수가 아니다. 기존 글 갱신도 포함한다. 반복 실행에서 `saved_count=10`, `delta.stored=0`은 정상이다.
- `selected_post_sns`, `candidate_count`: 날짜 필터를 통과한 후보와 건수 제한 뒤 선택된 게시물. 다른 동 고정 글은 후보와 제한에서 제외한다.
- `pages_read`, `failed_pages`, `conflicting_post_sns`, `failures`: 읽은 페이지, 실패 구간 및 개별 실패 정보. 실패한 목록 페이지 뒤에도 순회를 계속하고 공지별 독립 트랜잭션으로 저장한다. HTTP 429는 요청을 중단한다.
- `scope_complete`: 지정한 페이지·날짜 범위의 성공 여부이며 게시판 전체 수집 완료를 뜻하지 않는다. 건수 제한으로 후보가 남거나 목록 변경·실패·충돌이 있으면 false이고 종료 코드 1이다. 잘못된 인자는 2다. `dry_run`의 true는 목록 점검 성공이며 상세 저장 성공을 보장하지 않는다.
- 동일 출처·게시물 고유 키와 기존 `save_notice_with_files`를 사용하므로 중복 삽입하지 않는다. 원문이 같으면 기존 AI 결과를 유지하고, 원문이 바뀌면 기존 변경 감지·보존·재처리 정책을 따른다. 다른 글을 일괄 숨기거나 삭제하지 않는다.

## 검증 기록

2026-10-10, 운영 DB와 분리된 임시 로컬 PostgreSQL에 실제 공식 게시판을 수집했다. 검증 종료 후 임시 DB는 제거했다.

| 실행 | 범위 | 저장 전 → 후 | 공개 전 → 후 | 저장 성공 | 실패 |
| --- | --- | --- | --- | --- | --- |
| 최초 | 1페이지, 등록일 2026-01-01 이후 | 0 → 10 | 0 → 10 | 10 | 0 |
| 같은 범위 재실행 | 위와 동일 | 10 → 10 | 10 → 10 | 10 | 0 |

실제 자료 검증은 원문·첨부 참조 저장 및 anon 공개 조회까지다. AI 모델을 호출하거나 운영 웹 데이터를 늘린 검증은 아니다.

자동화 검증:

- `wolgye1_backfill`: dry-run, 날짜 필터, 뒤쪽 페이지 보충, 고정 글 중복 제거, 반복 저장, 건수 제한. 공개 건수 0 → 1 → 3 → 3을 별도 assertion으로 확인한다.
- `wolgye1_backfill_page_failure`: 두 번째 페이지 실패 후 세 번째 페이지까지 저장, 실패 보고 및 종료 코드 확인.
- `wolgye1_backfill_preserve_ai`: 기존 요약·쉬운말 DB 행이 재수집 전후 동일하고 공개 상세에서도 유지되는지 확인.
- `test_wolgye1_board.py`: 잘못된 범위의 I/O 차단, 충돌한 고정 글 및 마지막 목록 점검 실패 보고. 잘못된 등록일 한 건은 실패로 기록하고 다른 정상 후보는 유지한다.

운영 반영 시 #107 시연 점검에 실제 실행 JSON의 범위·전후 건수를 첨부하고, 웹의 월계동 목록에서 늘어난 공지를 확인한다.

최종 검사 결과:

- 파이프라인 전체: 4,098 passed, skip 0. 이후 잘못된 등록일 방어를 보강하고 관련 단위/E2E 30개를 재검증했다.
- DB 스키마: 768 passed, skip 0. `uv run pytest -c pyproject.toml ../../supabase/tests -q`로 파이프라인 테스트 지원 모듈 경로를 적용했다.
- `uv run ruff check`, `git diff --check`: 통과.
- 모든 DB 검사는 별도 임시 DB에서 수행했다. 운영 DB 보충, 배포, PR 생성은 수행하지 않았다.

코드 리뷰 보강: 페이지 간 일반 행 중복은 누락 가능성이 있으므로 해당 페이지를 실패 범위에 기록하고 `scope_complete=false`로 보고한다. 고정 글의 정상 반복은 허용한다. 재현 테스트를 포함한 관련 단위/E2E 31개와 Ruff를 최종 확인했다.
